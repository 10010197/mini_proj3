## 1. 실패 분석

### 1.1 단계별 분류 — 어디서 실패했나

답변 가능 68문항을 **정답 문서의 순위**(검색)와 **LLM 채점**(생성)으로 나눴다.

| 단계 | correct | partial | wrong | 과잉 거절 | 합계 |
|---|---|---|---|---|---|
| **A. 검색 실패** — 정답 문서가 상위 6 밖 | 2 | 11 | 3 | 3 | **19** |
| **B. 순위 밀림** — 정답 문서가 4~6위 | 1 | 3 | 0 | 0 | **4** |
| **C. 검색 성공** — 정답 문서가 1~3위 | 18 | 26 | 1 | 0 | **45** |
| 합계 | 21 | 40 | 4 | 3 | 68 |

- **wrong·과잉 거절 7건 중 6건이 검색 단계(A)에서 나왔다.** 근거가 없을 때 지어내지 않고 거절하거나 "확인할 수 없다"고 답했다. 생성은 의도대로 동작했고, 고칠 곳은 검색이다.
  - 근거 충실도 0.923, 잘못된 인용 번호 0건이다.
- **partial 40건 중 26건은 검색에 성공하고도 답이 불완전했다(C).** 이 손실은 검색이 아니라 생성·채점 단계에 있다.
- A의 correct 2건(F13·F19)은 정답으로 표기하지 않은 다른 문서(같은 내용의 기사·공시)로 맞혔다. 정답 문서 표기가 완전하지 않다는 뜻이다(§2.4).

  - 생성 모델이 핵심 수치 1~2개만 답하고, 정답 기준에 있는 부가 조건(비율·기간·순위)을 빼는 경우가 많다.
  - 일부는 채점 기준이 엄격한 탓이다. 질문이 묻지 않은 세부까지 요구하는 경우가 있다(§2.4).
- **비교 문항의 손실은 생성 단계에 있다.**
  - 비교 문항의 Hit@3은 0.667~0.778로 검색은 대체로 성공했다.
  - 그런데도 비교 대상 한쪽만 답하거나, 같은 기관 인용을 '기관이 다르다'고 서술했다(C06).
- **시점·정정 공시 혼동**
  - 같은 회사의 같은 종류 공시가 여러 해, 정정 전후로 함께 들어오면 어느 시점 수치인지 구분하지 못한다.
  - 공시 머리말에 대상 사업연도와 '정정 전/후'를 넣는 것이 검색(§1.2)과 생성 모두에 필요하다.

## 2. 한계

### 2.1 지식베이스·데이터

- **출처 편향**
  - 지식베이스 15,379건 중 뉴스가 52%, 1차 근거(공시+정부 보도자료)는 17%다.
  - 산업보고서(731건)는 BioIN 게시물 본문만 있다. 증권사 리서치와 첨부 PDF는 없어서, 시장 전망 수치의 출처가 일부 기관 인용에 몰린다.
- **기간·시점 편향**
  - 2021년은 10월부터, 2026년은 11월 초까지만 포함한다.
  - 문서 수가 최근 연도로 갈수록 많아(2021년 379건 → 2026년 3,616건) 시점 조건이 없는 질문은 최근 문서 쪽으로 기운다.
- **하위 주제 불균형**
  - 바이오 투자·CDMO·비대면 진료에 몰려 있다. 적은 주제(신약 기술수출 등)는 정답 문서를 놓치면 대체할 문서가 없다.
- **선별 손실**
  - 뉴스는 중복 처리 후 22,623건 중 8,001건만 넣었다(분기 층화).
  - 선별에서 빠진 기사에만 있는 사실은 답할 수 없다.
- **수집 범위**
  - 의료 AI 특허는 주제별 할당(600건)만 넣었다.
  - 해외 특허는 미국·유럽 242건뿐이다.
  - 블로그·커뮤니티는 수집하지 않았다([kb_composition.md](kb_composition.md)).

### 2.2 검색

- **종합 질문**: 질의 하나로 여러 쟁점의 근거를 고르게 모으지 못한다. 재정렬은 오히려 근거를 한쪽으로 몰아 근거 충실도가 0.94에서 0.6 전후로 떨어졌다(§7.4).
- **연도별·정정 공시 구분**: 같은 회사의 비슷한 공시가 여러 해 있으면 대상 사업연도를 구분하지 못한다. 공시 머리말에 대상 연도가 없다.
- **표현 불일치**: 동의어·공시 분류명을 질의 확장으로 처리하지 않는다('출자' ↔ '타법인 주식 취득').
- **유사도 점수의 변별력**: 같은 도메인에서는 코사인 유사도가 0.4~0.7에 몰려 있다. 그래서 점수만으로 '근거 없음'을 판단할 수 없다.
- **재정렬**
  - LLM 호출이라 비결정적이다. Hit@3이 실행마다 0.735~0.765로 달라진다.
  - 문항당 입력 약 1.1만 토큰이 더 들고, 지연이 +1.4초 늘어난다.

### 2.3 생성

- **부가 조건 누락**: 핵심 수치만 답하고 비율·기간·순위 같은 부가 조건을 빠뜨린다(§1.3의 17건).
- **비교 문항의 부분 답변**: '답할 수 있는 부분만 답한다' 규칙이 있어도 비교 축을 잘못 잡거나 한쪽만 답한다.
- **범위 밖 거절 위치(U08)**: 거절 표시를 맨 앞에 두라는 규칙이 질문 유형에 따라 지켜지지 않는다.
- **생성 모델 비교 안 함**: 생성 모델은 `gpt-5.4-mini` 하나로만 측정했다(`--chat-model gpt-5.4` 비교는 하지 않음).

### 2.4 평가

- **LLM 채점만 있음**
  - 정확도·근거 충실도는 `gpt-5.4` 채점 결과다.
  - 사람 검토용 CSV의 `manual_score`는 모든 실행에서 비어 있다(0/79). 사람 채점으로 보정하지 않았다.
  - 채점자는 부가 조건이 빠지면 partial을 주는 경향이 있어 정확도가 엄격하게 나온다.
- **측정 잡음**
  - 같은 설정을 다시 돌려도 정확도가 최대 0.05 달라진다(dense 3회 0.537~0.588).
  - 정확도 차이가 0.05보다 작은 설정 비교는 결론을 내리지 않았다. 대부분 1회 실행만 했다.
- **표본 크기**
  - 평가셋은 79문항이다. 비교·종합은 9문항씩이라 1문항이 0.11에 해당한다.
  - 유형별 수치는 방향을 보는 용도이고, 통계적 유의성은 없다.
- **정답 표기의 한계**
  - 정답 문서를 문항당 1~2개로 적었다. 종합 질문처럼 맞는 문서가 여럿이면 Hit@k가 손실을 과장한다(S04).
  - 반대로 표기하지 않은 문서로 맞히는 경우도 있다(F13·F19).
- **평가셋 오류**: U10은 지식베이스 보강 후 답변 가능해졌는데 아직 답변 불가로 분류돼 있다.
- **평가셋 작성자**: 평가셋은 개발자가 지식베이스를 보며 작성했다. 실제 사용자 질문 분포와 다를 수 있다.

### 2.5 시스템·운영

- **캐싱 미구현**
  - 검색 탭은 Streamlit이 다시 실행될 때마다 같은 검색어를 다시 임베딩한다.
  - 계층 검증에서 검색 1회·대화 1회 동안 같은 검색어가 7번 임베딩됐다.
  - 질의 임베딩·검색 결과 캐시는 심화 확장으로 남겼다.
- **지연**: 기본 설정의 지연 중앙값은 2.0초, p90은 3.6초다(검색+생성, 스트리밍 전 대기 포함). 재정렬을 쓰면 3.5초다.
- **Chroma 열기의 부수 기록**
  - chromadb 클라이언트를 열면 내부 잠금 테이블(`acquire_write`)에 한 행이 추가된다. 그래서 `chroma.sqlite3`의 수정 시각이 바뀐다.
  - 색인 내용(컬렉션·임베딩·메타데이터)은 바뀌지 않는다(§3.3). chromadb에는 읽기 전용 열기 모드가 없다.
- **멀티턴 평가 안 함**: 대화 맥락이 있을 때 후속 질문 재작성(`chain.condense`)은 앱에서 확인만 했다. 하네스는 단일 질문으로만 평가한다.
- **비용 의존**: 질의 임베딩·생성·채점이 모두 OpenAI API다. 키 없이는 검색 탭도 동작하지 않는다. 다만 성능 분석 탭은 동작한다.

### 3.2 방법 — `eval/check_layers.py`

```bash
python -m eval.check_layers            # 정적 + 실행 (질의 임베딩·답변 생성 API 호출 있음, 약 1분)
```

```bash
python -m eval.check_layers --static   # 정적 검사만
```

**정적 검사**: 각 계층의 모든 `.py`를 AST로 읽는다. 함수 안의 지연 import까지 포함해 다음을 찾는다.
- 금지 import
- 쓰기 호출: `add_texts`, `add_documents`, `upsert`, `embed_documents`, `get_or_create_collection` 등
- 쓰기 SQL 문자열: `INSERT`, `UPDATE`, `CREATE` 등

### 3.4 검증 중 확인한 사항

- **`langchain_chroma.Chroma()`는 내부에서 `get_or_create_collection`을 부른다.**
  - 컬렉션 이름이 틀리면 챗봇이 빈 컬렉션을 **새로 만들 수 있는** 경로다.
  - `rag/retriever.vectorstore()`는 이 호출 전에 컬렉션 목록을 확인하고, 없으면 오류로 멈춘다. 그래서 실제로는 조회만 일어난다.
  - 실행 검사는 '새로 만드는 경우'만 차단하도록 구분했다.
- **`OpenAIEmbeddings.embed_query`는 내부에서 `embed_documents([질문])`을 부른다.**
  - 이름만 보면 문서 임베딩 같지만 질의 임베딩이다. 실행 검사는 `embed_query`를 거친 질문 1개 호출만 허용했다.
  - 챗봇 코드에는 `embed_documents`를 직접 부르는 곳이 없다(정적 검사).
- **chromadb 클라이언트를 열 때마다 내부 `acquire_write` 테이블에 1행이 추가된다.**
  - 그래서 `chroma.sqlite3` 수정 시각이 바뀐다. 파일 크기와 나머지 20개 테이블(임베딩·메타데이터·컬렉션)은 그대로다.
  - 라이브러리의 잠금 기록이므로 인덱스 쓰기로 보지 않았다. 대신 결과 파일에 `chroma_internal_changes`로 남긴다(§2.5).
- **docs.db는 앱의 모든 연결이 `mode=ro`다.**
  - `rag/retriever.get_document`, `app/dashboard.load_kb` 모두 읽기 전용 연결이다.
  - 실행 중 쓰기 모드 연결은 0건이었다.
