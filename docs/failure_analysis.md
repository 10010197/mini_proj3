## 1. 개선 루프와 실험 기록

```
측정 → 실패 사례 확인 → 원인 계층 특정 → 단일 변수 변경 → 재측정
```

| 단계 | 도구 | 산출물 |
|---|---|---|
| 측정 | `python -m eval.run_eval --tag <태그>` (챗봇과 같은 `rag.chain.ask`) | `eval/results/answer_eval_<태그>.json`, 사람 검토용 `answer_review_<태그>.csv` |
| 실패 사례 확인 | 성능 분석 탭 → 질문 유형별 → 실패 사례 (답변 원문·채점 이유) | — |
| 원인 계층 특정 | `python -m eval.diagnose_failures --tag <태그>` | `eval/results/failure_layers__<태그>.json` (§2) |
| 단일 변수 변경 | 검색 변수는 먼저 `python -m eval.sweep_retrieval --param <변수>`로 순위만 측정 | `eval/results/retrieval_sweep__<변수>.json` |
| 재측정 | 순위가 좋아진 값만 `run_eval`로 생성·채점까지 | 새 태그 |

**실험 기록 — [eval/experiments.json](../eval/experiments.json)**
- 결과 태그마다 부모 실험, 원인 계층, 바꾼 변수 하나, 결정을 적는다.
- 성능 분석 탭의 실험 목록도 이 파일에서 읽는다.

| 실험 (태그) | 부모 | 계층 | 바꾼 변수 하나 | 결과 · 결정 |
|---|---|---|---|---|

| `fixed__gpt-5.4-mini` | 재실행 | 인덱싱 | 청킹 방식 structure → fixed | **기각**: Hit@3 −7.4%p |
| `structure_notitle__gpt-5.4-mini` | 재실행 | 인덱싱 | 청크 머리말 포함 → 제외 | **기각**: Hit@3 −20.6%p (머리말 유지) |
| `structure__dense__gpt-5.4-mini` | 재실행 | — | 없음 (검색기 보완 후 기준 재측정) | hybrid 비교 기준 |
| `structure__hybrid__gpt-5.4-mini` | dense 재실행 | 검색 | dense → dense + BM25 | **채택 후 확장**: Hit@1 +13.2%p |
| `structure__hybrid_time__gpt-5.4-mini` | hybrid | 검색 | 질문 연도 목록 추가 | **채택**: Hit@3 0.603 → 0.662 |
| `structure__hybrid_rerank__gpt-5.4-mini` (+`_run2`) | hybrid_time | 검색 | LLM 재정렬 | **보류**: Hit@3 0.735, 종합 근거 충실도 하락·지연 +1.4초 |
| `structure__hybrid_time__gpt-5.4-mini_prompt2` ★ | hybrid_time | 생성 | 시스템 프롬프트 | **채택(현재 기본)**: 정확도 같음, 과잉 거절 0.059 → 0.044 |
| `retrieval_sweep__pool` (순위만) | ★ | 검색 | 후보 청크 수 pool 40 → 80·160·400 | **기각**: Hit@3 0.662 → 0.662·0.647·0.662 |

- 모든 실험이 부모 대비 변수 하나만 바꿨다.
- 예외가 하나 있다. 기준선 재실행과 dense 재실행 사이에 검색기 보완(문서가 모자라면 pool을 5배로 넓혀 재조회, F31 한 문항 해당)이 들어갔다.
  - 그래서 hybrid 계열은 보완 후 다시 잰 dense를 부모로 삼았다.
- **pool 스윕 (2026-11-10)**
  - 진단(§2)에서 F08·F15는 넓은 검색에서는 1위인데 실제 답변 근거 상위 6에는 없었다. 그래서 후보 pool 크기를 의심했다.
  - pool=40 값은 하네스 결과(Hit@3 0.662, MRR 0.595)를 그대로 재현했다. 측정이 맞다는 확인이다.
  - pool을 400으로 넓히면 F08·F15를 얻지만 F21·S04를 잃는다. Hit@3 순증이 0이다.
  - 그래서 생성·채점 재측정(문항 79개 × 생성·채점 비용)은 하지 않았다. **pool은 40을 유지한다.**

## 2. 실패 원인 계층 진단

### 2.1 판정 규칙 — `eval/diagnose_failures.py`

실패 문항마다 증상을 증거로 확인해 원인 계층을 하나 정한다. 판정은 위에서부터 순서대로 한다.
- 실패 문항의 정의
  - 답변 가능 문항: Hit@3 실패이거나 채점이 correct가 아닌 문항
  - 답변 불가 문항: 거절하지 않은 문항

| 증상 | 원인 계층 | 판정 증거 |
|---|---|---|
| 검색 결과에 정답 문서가 포함되지 않음 — 문서 부재 | 데이터 | 정답(별칭·같은 사건·정정 전후 포함) 문서가 docs.db에 없음(수집) 또는 `in_kb=0`(선별) |
| 정답 문서가 존재하나 검색되지 않음 | 인덱싱 | 지식베이스·Chroma에 있으나 넓은 검색(같은 검색 방식, 상위 60문서)에도 없음 |
| 검색은 되었으나 순위가 낮음 | 검색 | 넓은 검색 60위 안에는 있으나 답변 근거 상위 3 밖 (4~6위 포함) |
| 근거는 정확하나 답변이 부정확함 | 생성 | 정답 문서가 1~3위인데 채점이 correct가 아님 |
| 근거 없는 내용을 생성함 | 생성 (보조 표시) | 근거 충실도 < 1 |
| 검색 결과 상위가 동일 내용으로 채워짐 | 전처리 (보조 표시) | 상위 6문서 중 같은 내용 쌍(같은 사건·정정 전후·본문 5-gram 유사도 ≥ 0.5)이 2쌍 이상 |

- 검색 재현에는 질의 임베딩만 쓴다. 생성과 채점은 다시 하지 않는다.
- 판정 계층은 **증상이 드러난 곳**이다. 대응은 다른 계층에서 해야 할 수 있다. 예: 연도별 공시 혼동은 검색 증상이지만 대응은 공시 머리말(인덱싱)이다.

### 2.2 결과 — 현재 기본 설정 (`structure__hybrid_time__gpt-5.4-mini_prompt2`)

| 원인 계층 | 실패 | 문항 |
|---|---|---|
| 데이터 | **0** | — 정답 문서는 모두 지식베이스와 인덱스에 있다 |
| 전처리 (주 원인) | **0** | 보조 표시 7건은 §2.4 |
| 인덱싱 | **2** | C07 · S05 |
| 검색 | **21** | 4~6위: F04 F05 F12 T08 / 6위 밖·넓은 검색 7~8위: F08 F15 F19 C02 T12 / 17~31위: F13 F17 C05 T01 T04 S01 S02 S07 / 40~52위: T02 T10 S03 S08 |
| 생성 | **28** | 답변 부정확 27: F06 F07 F11 F16 F18 F22 F27 F29 F30 F31 F32 F33 C01 C03 C04 C06 C08 C09 T05 T06 T07 T11 T13 T14 S04 S06 S09 / 거절 실패: U08 |
| 평가셋 | **1** | U10 (지식베이스 보강 후 근거가 생김) |
| **합계** | **52** | 답변 가능 50 + 답변 불가 2 (답변 가능 68 중 correct이면서 Hit@3인 문항은 18개) |

- 근거 없는 내용(근거 충실도 < 1)은 10건이다: F04 F12 C03 C06 C07 C09 S02 S05 F30 T13.
  - 모두 일부 주장만 근거 밖이다(0.5). 전부 근거 밖인 경우(0)는 없다. 잘못된 인용 번호도 0건이다.

**결론: 실패는 검색(21)과 생성(28)에 몰려 있다.** 데이터·전처리 계층의 실패는 없다.
- 그래서 추가 수집이나 중복 처리 기준을 바꾸는 것은 다음 개선 대상이 아니다.
- 또한 이 진단은 표의 '답변 품질 문제로 모델 변경 전 검색 결과를 먼저 확인한다'는 지침과 맞는다.
  - 생성 실패 27건은 모두 정답 문서를 1~3위로 받은 문항이다.
  - 따라서 이 27건은 모델 교체보다 프롬프트(답변 구성 규칙)를 바꿀 대상이다.

- 생성 계층의 다음 실험은 **프롬프트 한 가지만 바꾸는 `prompt3`** 이다.
  - 검색은 `hybrid_time`으로 고정해, 개선이 프롬프트 효과인지 구분할 수 있게 한다.
  - **사람 채점 후 우선순위를 조정했다(§2.5).**
    - 사실·시점 문항의 '세부 요소 누락'은 사람 채점에서 6건 중 5건이 정답(1점)이다. 실패가 아니라 LLM 채점 기준이 엄격한 탓이다.
    - 그래서 prompt3는 '부가 조건 포함'보다 다음을 겨냥한다.
      - 종합 문항의 쟁점 구성 (S04·S06·S09는 사람도 0.5)
      - 비교 문항에서 한쪽만 답하는 경우 (C03)
- 검색·인덱싱 실험과 같이 돌리지 않는다.
- '공시 머리말에 대상 사업연도' 변수는 검색(F13 T01 T02 T04)과 생성(F16 F11 T05 F07) 실패 8건에 함께 걸린다.
  - 다만 재청킹·재임베딩이 필요하다(설정당 약 25분).

**인덱싱 2건** — 점검표의 '청크 크기, 제목 포함 여부'를 직접 확인했다.
- C07(루닛·뷰노 특허 분야 비교)
  - 정답 특허 청크 머리말에 발명의 명칭·출원인(주식회사 루닛)·IPC가 들어 있다. 청크 문제가 아니다.
  - 지식베이스에 루닛 특허가 42건 있어서, '주로 어떤 분야인가'는 여러 문서를 집계해야 답할 수 있다. 상위 k개 검색으로는 집계를 할 수 없다.
  - → 출원인 메타데이터 필터 + IPC 집계 같은 별도 도구가 필요하다. 현재 범위 밖이므로 한계로 둔다(§3.2).
- S05('국내 기업들은 ADC 기술을 어떤 방식으로 확보하나')
  - 정답 공시 청크의 머리말·본문은 정상이다.
  - 질문이 넓고, 정답이 회사별 공시 4개에 흩어져 있다. 성격이 종합 질문 검색 실패와 같다 → 다중 질의 대상이다.

**평가셋 1건 (U10)** — 지식베이스를 보강하면서 근거(보건복지부 보도자료가 인용한 건보공단 만족도 조사)가 생겼다. 평가셋을 고쳐야 한다(§3.4).

### 2.4 전처리 — 상위가 같은 내용으로 채워지는가

| 상위 6문서 중 같은 내용 쌍 수 | 0쌍 | 1쌍 | 2쌍 | 3쌍 이상 |
|---|---|---|---|---|
| 문항 수 (전체 79) | 51 | 15 | 5 | 8 |

- 2쌍 이상인 실패 문항은 7개다: F07 · C04 · F16 · F08 · C02 · F05 · C03.
- 내용을 확인해 보니 대부분 **재배포 중복이 아니라 같은 양식의 서로 다른 공시**다.
  - F07: 'LCB97 마일스톤 기술료 수령' 공시 5건. 2024-11 ~ 2026-07, 회차마다 금액이 다르다.
  - C04: 삼성바이오로직스 '의약품 위탁생산계약' 공시 6건.
  - 이 공시들은 서로 다른 사실이라 지우면 안 된다. 그래서 중복 처리 기준을 다시 정할 대상이 아니다.
- 정정 전후 공시가 함께 들어온 경우(F16 3쌍, F05·C02)는 실제로 같은 내용이다. 현재는 평가에서 서로를 정답으로 인정한다. 다만 생성에서는 F16처럼 어느 수치를 답할지 헷갈린다.
  - → 대응: 정정 공시를 원 공시와 묶어 하나의 근거로 넘기기. 공시 머리말 변수와 같은 인덱싱 작업이다.
- 결론: 전처리(중복 처리) 계층의 주 원인 실패는 0건이다. 같은 양식 공시가 상위를 차지하는 문제는 검색 다양화(회사·공시 종류별 상한) 쪽이다.

## 3. 한계

### 3.1 지식베이스·데이터

- **출처 편향**
  - 지식베이스 15,379건 중 뉴스가 52%, 1차 근거(공시+정부 보도자료)는 17%다.
  - 산업보고서(731건)는 BioIN 게시물 본문만 있다. 증권사 리서치와 첨부 PDF는 없어서, 시장 전망 수치의 출처가 일부 기관 인용에 몰린다.
- **기간·시점 편향**
  - 2021년은 10월부터, 2026년은 11월 초까지만 포함한다.
  - 문서 수가 최근 연도로 갈수록 많아(2021년 379건 → 2026년 3,616건) 시점 조건이 없는 질문은 최근 문서 쪽으로 기운다.
- **하위 주제 불균형**
  - 바이오 투자·CDMO·비대면 진료에 몰려 있다. 적은 주제(신약 기술수출 등)는 정답 문서를 놓치면 대체할 문서가 없다.
- **선별 손실**
  - 뉴스는 중복 처리 후 22,623건 중 8,001건만 넣었다(분기 층화).
  - 선별에서 빠진 기사에만 있는 사실은 답할 수 없다.
- **수집 범위**
  - 의료 AI 특허는 주제별 할당(600건)만 넣었다.
  - 해외 특허는 미국·유럽 242건뿐이다.
  - 블로그·커뮤니티는 수집하지 않았다([kb_composition.md](kb_composition.md)).

### 3.2 검색

- **종합 질문**: 질의 하나로 여러 쟁점의 근거를 고르게 모으지 못한다. 재정렬은 오히려 근거를 한쪽으로 몰아 근거 충실도가 0.94에서 0.6 전후로 떨어졌다([evaluation.md](evaluation.md) §7.4).
- **연도별·정정 공시 구분**: 같은 회사의 비슷한 공시가 여러 해 있으면 대상 사업연도를 구분하지 못한다. 공시 머리말에 대상 연도가 없다.
- **표현 불일치**: 동의어·공시 분류명을 질의 확장으로 처리하지 않는다('출자' ↔ '타법인 주식 취득').
- **유사도 점수의 변별력**: 같은 도메인에서는 코사인 유사도가 0.4~0.7에 몰려 있다. 그래서 점수만으로 '근거 없음'을 판단할 수 없다.
- **집계형 질문**: '루닛 특허는 주로 어떤 분야인가'(C07)처럼 여러 문서를 세어야 하는 질문은 상위 k개 검색으로 답할 수 없다. 출원인 필터와 IPC 집계 같은 별도 도구는 구현하지 않았다.
- **재정렬**
  - LLM 호출이라 비결정적이다. Hit@3이 실행마다 0.735~0.765로 달라진다.
  - 문항당 입력 약 1.1만 토큰이 더 들고, 지연이 +1.4초 늘어난다.

### 3.3 생성

- **부가 조건 누락**: 핵심 수치만 답하고 비율·기간·순위 같은 부가 조건을 빠뜨린다(§2.3의 17건).
- **비교 문항의 부분 답변**: '답할 수 있는 부분만 답한다' 규칙이 있어도 비교 축을 잘못 잡거나 한쪽만 답한다.
- **범위 밖 거절 위치(U08)**: 거절 표시를 맨 앞에 두라는 규칙이 질문 유형에 따라 지켜지지 않는다.
- **생성 모델 비교 안 함**: 생성 모델은 `gpt-5.4-mini` 하나로만 측정했다(`--chat-model gpt-5.4` 비교는 하지 않음).

### 3.4 평가

- **사람 채점은 표본 30문항뿐**
  - 정확도·근거 충실도의 전체 79문항 값은 `gpt-5.4` 채점 결과다.
  - 사람 채점은 현재 기본 실행의 블라인드 층화 표본 30문항만 했다(§2.5).
  - 사람 기준 전체 정확도 0.795는 유형별 가중 추정치다. 유형당 5~14문항이라 오차가 크다.
  - 근거 충실도는 사람이 채점하지 않았다.
  - 다른 실행(실험 9개)은 사람 채점이 없다. 실험 간 비교는 같은 LLM 채점자 기준이다.
  - LLM 채점의 차이는 한 방향(엄격)으로 치우쳐 있다. 그래서 상대 비교에는 쓸 수 있지만, 절대값은 사람 기준보다 약 0.2 낮다.
- **측정 잡음**
  - 같은 설정을 다시 돌려도 정확도가 최대 0.05 달라진다(dense 3회 0.537~0.588).
  - 정확도 차이가 0.05보다 작은 설정 비교는 결론을 내리지 않았다. 대부분 1회 실행만 했다.
- **표본 크기**
  - 평가셋은 79문항이다. 비교·종합은 9문항씩이라 1문항이 0.11에 해당한다.
  - 유형별 수치는 방향을 보는 용도이고, 통계적 유의성은 없다.
- **정답 표기의 한계**
  - 정답 문서를 문항당 1~2개로 적었다. 종합 질문처럼 맞는 문서가 여럿이면 Hit@k가 손실을 과장한다(S04).
  - 반대로 표기하지 않은 문서로 맞히는 경우도 있다(F13·F19).
- **평가셋 오류**: U10은 지식베이스 보강 후 답변 가능해졌는데 아직 답변 불가로 분류돼 있다.
- **평가셋 작성자**: 평가셋은 개발자가 지식베이스를 보며 작성했다. 실제 사용자 질문 분포와 다를 수 있다.

### 3.5 시스템·운영

- **캐싱 미구현**
  - 검색 탭은 Streamlit이 다시 실행될 때마다 같은 검색어를 다시 임베딩한다.
  - 계층 검증에서 검색 1회·대화 1회 동안 같은 검색어가 7번 임베딩됐다.
  - 질의 임베딩·검색 결과 캐시는 심화 확장으로 남겼다.
- **지연**: 기본 설정의 지연 중앙값은 2.0초, p90은 3.6초다(검색+생성, 스트리밍 전 대기 포함). 재정렬을 쓰면 3.5초다.
- **Chroma 열기의 부수 기록**
  - chromadb 클라이언트를 열면 내부 잠금 테이블(`acquire_write`)에 한 행이 추가된다. 그래서 `chroma.sqlite3`의 수정 시각이 바뀐다.
  - 색인 내용(컬렉션·임베딩·메타데이터)은 바뀌지 않는다(§4.3). chromadb에는 읽기 전용 열기 모드가 없다.
- **멀티턴 평가 안 함**: 대화 맥락이 있을 때 후속 질문 재작성(`chain.condense`)은 앱에서 확인만 했다. 하네스는 단일 질문으로만 평가한다.
- **비용 의존**: 질의 임베딩·생성·채점이 모두 OpenAI API다. 키 없이는 검색 탭도 동작하지 않는다. 다만 성능 분석 탭은 동작한다.

**정적 검사**: 각 계층의 모든 `.py`를 AST로 읽는다. 함수 안의 지연 import까지 포함해 다음을 찾는다.

- 쓰기 호출: `add_texts`, `add_documents`, `upsert`, `embed_documents`, `get_or_create_collection` 등
- 쓰기 SQL 문자열: `INSERT`, `UPDATE`, `CREATE` 등

**실행 검사**: 새 프로세스에서 아래처럼 막은 뒤, `streamlit.testing` AppTest로 **실제 `app/main.py`를 구동**한다.

|---|---|
| `collector`·`indexer` import | 차단하고 기록 |

### 4.4 검증 중 확인한 사항

- **`langchain_chroma.Chroma()`는 내부에서 `get_or_create_collection`을 부른다.**
  - 컬렉션 이름이 틀리면 챗봇이 빈 컬렉션을 **새로 만들 수 있는** 경로다.
  - `rag/retriever.vectorstore()`는 이 호출 전에 컬렉션 목록을 확인하고, 없으면 오류로 멈춘다. 그래서 실제로는 조회만 일어난다.
  - 실행 검사는 '새로 만드는 경우'만 차단하도록 구분했다.
- **`OpenAIEmbeddings.embed_query`는 내부에서 `embed_documents([질문])`을 부른다.**
  - 이름만 보면 문서 임베딩 같지만 질의 임베딩이다. 실행 검사는 `embed_query`를 거친 질문 1개 호출만 허용했다.
  - 챗봇 코드에는 `embed_documents`를 직접 부르는 곳이 없다(정적 검사).
- **chromadb 클라이언트를 열 때마다 내부 `acquire_write` 테이블에 1행이 추가된다.**
  - 그래서 `chroma.sqlite3` 수정 시각이 바뀐다. 파일 크기와 나머지 20개 테이블(임베딩·메타데이터·컬렉션)은 그대로다.
  - 라이브러리의 잠금 기록이므로 인덱스 쓰기로 보지 않았다. 대신 결과 파일에 `chroma_internal_changes`로 남긴다(§3.5).
- **docs.db는 앱의 모든 연결이 `mode=ro`다.**
  - `rag/retriever.get_document`, `app/dashboard.load_kb` 모두 읽기 전용 연결이다.
  - 실행 중 쓰기 모드 연결은 0건이었다.
